# Memory Kit 规范 v1

一套用于长期项目记忆的轻量契约：**一份源文件，三种视图，五类内容，四级证据**。
零依赖（Node 18+），可以整个目录复制到任何项目。

---

## 1. 为什么需要契约

绝大多数"项目记忆"最后都会退化成一篇越来越长的文章，原因是它同时装了三类寿命完全不同的内容：

| 内容 | 例子 | 寿命 | 正确的编辑动作 |
| --- | --- | --- | --- |
| 事实与状态 | 设备端口、依赖版本、产物路径 | 变了就作废 | 覆盖，并更新核对日期 |
| 事件记录 | 某次运行的报错和结论 | 永不改变 | 只追加 |
| 待办与路线 | 下一步做什么 | 做完就消失 | 完成即删除 |

混在一起时，你无法回答三个最基本的问题：**哪一条已经过期？上一次会话新增了什么？还有哪些结论没有验证？**
契约的作用就是把这三类内容分开标注，让机器能替你回答。

## 2. 一个单元

```
memory/
├── memory.config.json        # 清单：有哪些单元、映射到站点的哪个课程
├── README.md                 # 本项目的使用说明
├── index.md                  # 生成物：单元索引与健康状态
└── <unit-id>/
    ├── unit.md               # 唯一正文源
    └── vars.local.json       # 机器相关变量真值（不提交）
```

- **一个单元 = 一个主题**（一门课、一篇论文、一个工程实践、一个项目）。不要把所有主题塞进一个单元。
- **`unit.md` 是唯一正文源**。网页、摘要、下载文件都从它派生，不允许反向手改生成物。
- **`vars.local.json` 只存在于本机**。换一台机器，只需重写这个文件，正文不必修改——这是"可迁移"的全部含义。

### 2.1 文件结构

```markdown
<!--memory
{ ...JSON 头部... }
-->

# 标题

## 0. 导航          ← 必须是第 0 章
### 0.1 ...
## 1. 事实与状态
### 1.1 ...
## 2. ...
```

- 二级标题 `## N. 标题` 切章，编号必须从 0 开始且连续。
- 三级标题 `### N.M 标题` 是小节；编号可选，但写了就必须与所属章一致。
- 首个二级标题之前的内容并入第 0 章。
- 支持的块：段落、`###`/`####` 标题、代码块、表格、有序/无序列表、`>` 引文。
- 支持的 inline：行内代码、`[文字](https)` 链接、`**粗体**`、`$...$` 数学（需在头部开启 `math`）。
- 整行 `<!-- ... -->` 是作者注释，不会出现在输出里。

### 2.2 头部字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✓ | kebab-case，与目录名一致 |
| `title` | ✓ | 单元标题 |
| `kind` | ✓ | `course` / `paper` / `practice` / `project` / `reference` |
| `created` | ✓ | `YYYY-MM-DD` |
| `updated` | ✓ | 最后一次**核对**的日期，不是最后一次改字 |
| `visibility` | ✓ | `local`（可含本机信息）或 `public`（必须无本机路径与密钥） |
| `chapterTypes` | 建议 | `{"0":"guide","1":"facts",...}`，逐章声明类型 |
| `idPrefix` | 建议 | 生成锚点用，例如 `so` → `so3-1` |
| `math` | 否 | `true` 时启用 `$...$` |
| `vars` | 否 | 变量的便携默认值（真值放 `vars.local.json`） |
| `requireChapterZero` | 否 | 默认 `true`；纯数据单元可设为 `false` |

## 3. 章节类型

类型不是装饰，它决定**这一章该怎么维护**，也决定校验规则。

| 类型 | 装什么 | 更新纪律 | 校验 |
| --- | --- | --- | --- |
| `guide` | 范围、学习路径、阅读顺序 | 结构变了才改 | — |
| `facts` | 当前事实、设备状态、版本 | 覆盖式更新，必须写核对日期 | 必须有表格与证据标记 |
| `session` | 某次会话/实验的记录 | **只追加**，永不改写 | — |
| `pitfalls` | 报错 → 原因 → 处理 | 累积，可合并同类 | — |
| `plan` | 待办、路线、待核对 | 完成即删除 | 必须有列表项 |
| `refs` | 外部资料 | 追加 | 必须有链接 |
| `tasks` | 已完成的小任务台账 | **只追加**，完成即记 | 必须有 日期/任务/结果 三列的表格 |

经验法则：**写"现在是什么"就是 facts，写"发生过什么"就是 session。** 拿不准时按 session 写，因为它只追加，不会污染事实。

## 4. 证据等级

记忆的价值不在结论，而在结论背后的证据强度。统一使用五级：

| 等级 | 名称 | 判定标准 | 不能用来证明 |
| --- | --- | --- | --- |
| `E0` | 计划或推测 | 尚未执行，只是设想 | 任何已完成状态 |
| `E1` | 文档 | 官方文档、规范、论文的通用说明 | 本机版本的具体行为 |
| `E2` | 源码或日志 | 本机版本源码，或某一次真实运行的终端输出 | 可重复性；单次日志不等于稳定行为 |
| `E3` | 产物或模拟 | 磁盘上真实存在的产物，或隔离运行的模拟测试 | 实机正确性；模拟通过不等于真实可用 |
| `E4` | 实机人工确认 | 在真实设备/真实环境中由人确认过 | 泛化性；一次成功不等于每次都成功 |

使用规则：

1. `facts` 的每一行都应能回答"证据是什么等级、何时核对"。
2. **不得跨级表述**：E3 的产物不能写成"已验证可用"，E2 的单次日志不能写成"总是失败"。
3. 报告进度时按等级逐层声明，例如"配置解析通过（E2），真实读帧通过（E4）"。
4. 等级只升不降；降级意味着发现了反例，应作为 `session` 记录下来再改 `facts`。

## 5. 变量与可见性

正文里不写本机绝对路径、串口、序列号，写成 `{{NAME}}`：

```markdown
数据集保存在 `{{DATA_DIR}}`，从臂串口是 `{{FOLLOWER_PORT}}`。
```

同目录 `vars.local.json` 提供真值：

```json
{ "DATA_DIR": "/Users/me/data", "FOLLOWER_PORT": "/dev/cu.usbmodem1234" }
```

- `local` 模式：替换为真值，页面照常显示，用于本机阅读。
- `public` 模式：一律替换成 `‹NAME›`，用于对外发布。
- 没有真值时始终显示 `‹NAME›`，并在校验中报"未解析变量"。
- `visibility: public` 的单元若正文出现 `/Users/...`、`usbmodem...`、疑似密钥，校验直接失败。

这样同一份记忆可以在三台机器上只有一份 diff——就是 `vars.local.json`。

## 6. 入口、视图与产物

项目根目录的 **`BootMemory.md` 是引导程序**：它不存状态，只规定启动顺序（自检 → 找记忆 → 加载 → 校验 → 移交），并在找不到 `memory/` 时提供首次安装流程。它和本套件相互独立——没有 `memory-kit` 也能按它启动和安装，只是失去自动校验。

记忆本身有三种读数方式：

| 视图 | 命令 | 用途 |
| --- | --- | --- |
| 当前状态 | `npm run memory:index` | `memory/index.md`：单元表、每个单元的前几条未完成项、校验状态；加 `--full` 才附状态表 |
| 网页课程 | `npm run build` | 人读，长篇、带排版、进站点搜索（需要 `site` 配置） |
| 摘要 | `npm run memory:digest` | Agent 或接续会话读，压缩到几百字 |

外加第四种：**源文件本身**就是可下载、可复制的模板，含契约头部，拿走即用。

分界原则：**BootMemory 稳定、index 易变**。凡是"今天变成什么样"的内容都属于 index，不属于 BootMemory；否则引导区会随着项目进展不断失修。

## 7. 校验规则

`memory.mjs check` 分两级。

**错误（阻断构建）**

- 缺少或无法解析 `<!--memory ...-->` 头部
- `memory.config.json` 里的 `id` 与单元头部的 `id` 不一致（索引会指向两个名字）
- 必填字段缺失、`id` 非 kebab-case、日期非 `YYYY-MM-DD`、枚举值非法
- 章节不从 0 开始或不连续；小节编号与所属章不一致
- `chapterTypes` 指向不存在的章节
- 代码围栏未闭合；表格缺少分隔行或列数不一致
- `tasks` 章节没有表格，或表头缺少 日期 / 任务 / 结果
- 链接使用 http/https 以外的协议
- `visibility: public` 时出现本机路径、设备号或密钥
- 变量未解析（仅当显式 `--require-vars`）

**警告（不阻断）**

- `facts` 章没有表格或没有证据标记
- `plan` 章没有列表项；`refs` 章没有链接
- 某章未声明类型
- 变量未解析（默认情况）
- 超过 `staleAfterDays`（默认 30）天未核对

设计取舍：宁可少报也不误报。会让构建失败的条件，必须是"内容一定错了"，而不是"写法不够好"。

## 8. 把一份旧记忆变成单元

1. 新建 `memory/<id>/unit.md`，粘入原文。
2. 在顶部加 `<!--memory {...}-->`，填 `id/title/kind/created/updated/visibility`。
3. 通读一遍，给每章标 `chapterTypes`。这一步会暴露"事实和日志混在一起"的地方。
4. 把本机路径、端口、序列号替换成 `{{变量}}`，真值写进 `vars.local.json`。
5. 给 `facts` 的表格补上"证据"和"核对"两列，用 E0–E4 标注现状。
6. 跑 `memory.mjs check`，修到 0 错误；按警告逐条决定是否处理。

## 9. 接入另一个项目

最小接入只有一个文件：把 `BootMemory.md` 复制到新项目根目录。之后第一次对它说"请阅读 BootMemory.md"，它会按第 5 节现场安装 `memory/`。

要自动化再复制工具：

```sh
cp -R memory-kit /path/to/project/
cd /path/to/project
node memory-kit/bin/memory.mjs new first-unit --title "第一个单元"
cat > memory/memory.config.json <<'JSON'
{ "version": 1, "staleAfterDays": 30, "units": [{ "id": "first-unit", "file": "first-unit/unit.md" }] }
JSON
node memory-kit/bin/memory.mjs check
```

`site` 字段是可选的：没有它，这个单元只服务记忆本身（纯项目、无网站）。若要接入类似 STUDIUM 的站点，在 `memory.config.json` 的 `site` 里声明课程映射（`id/title/landingPage/pagePrefix/lead`），并可选地加 `download`；然后让构建脚本调用 `loadMemoryUnits()`，`buildCourse()` 返回的对象形状与站点现有课程一致。

## 10. 为什么是这些取舍

- **单文件而不是多文件**：编辑摩擦是记忆系统最大的敌人。多文件适合"三类内容更新频率差异极大且有人专职维护"的场合；对个人项目，一次编辑就要改四个文件，往往第二周就没人写了。
- **JSON 头部而不是 YAML**：零依赖解析，且能直接 `JSON.parse` 报出准确错误位置。YAML 需要额外依赖，出错时定位成本更高。
- **校验分级而不是全量严格**：严格校验会把"记忆写得诚实"变成负担，作者很快就会为了过检查而删掉不确定的内容——恰好与目标相反。
- **变量遮蔽而不是删掉本机信息**：本机信息对复现至关重要，只是不该被发布。遮蔽让同一份源既能自用也能公开。

## 11. 契约版本与升级

### 11.1 确认你装的是哪一版

```sh
node memory-kit/bin/memory.mjs version
```

输出工具版本、支持的契约版本与 Node 版本。工具版本写在 `memory-kit/VERSION`，随目录一起复制，所以每个项目都能自报版本；`check` 的抬头也会打印这两个号，`check --json` 里是 `kit.version` 与 `kit.contracts`。

判断某个项目是否落后于母本：

```sh
sh memory-kit/bin/selfcheck.sh; echo "exit=$?"
```

退出码：`0` 一致、`1` 落后、`2` 未安装、`3` 无法核对（无网络）、`4` 本地比母本新。

`raw.githubusercontent.com` 有 CDN 缓存，刚推送后可能几十秒内取到旧值，`contents` API 也在同一张缓存网络上。脚本的处理顺序：

1. 取 raw；与本地不一致时取 API 复核（两者都旧就说明仍在缓存窗口）。
2. 仍不一致则重试，默认 2 次、每次间隔 5 秒（`MEM_KIT_RETRIES` / `MEM_KIT_PAUSE` 可调）。
3. 仍不一致才下结论；若本地更新，提示"刚推送就等一分钟再看"。

结论是**建议性**的：`4` 只是提醒，不要据此覆盖本地更新的副本。更新方式见 `BootMemory.md` §4.2——整目录覆盖，数据不受影响。

需要离线核对时，把 `MEM_KIT_RAW` 指向本地版本文件：

```sh
MEM_KIT_RAW="file:///path/to/Mem-kit/memory-kit/VERSION" sh memory-kit/bin/selfcheck.sh
```

### 11.2 版本规则

单元头部有 `"memory": 1`，表示它遵循本规范的 v1。`check` 的规则：

- 缺少该字段 → 警告（旧单元仍可读）。
- 值不在工具支持列表里 → **错误**，提示先升级 `memory-kit`。宁可拒绝解析，也不要按旧规则猜新格式。

将来发布 v2 时按这个顺序做，避免把老单元读坏：

1. 先让工具**同时接受 v1 与 v2**，`meta.memory` 决定走哪条解析分支。
2. 提供 `memory.mjs migrate` 把 v1 单元原地升级（先备份，只改头部与结构性字段，不动正文）。
3. 全部单元迁移完成后，删除 v1 分支，再把 `memory` 提升为 2。

原则：**版本号是给工具看的，不是给人看的**。正文永远只写一种格式，兼容逻辑全部留在代码里。

## 12. 任务台账与进度可视化

### 12.1 为什么要有 tasks

`plan` 章只回答"还差什么"，任务完成后条目会被删掉——于是**做完了什么没有任何痕迹**。`tasks` 章补上这一半：每完成一个可验收的小任务，追加一行。

```markdown
## 5. 任务日志

| 日期 | 任务 | 结果 | 证据 | 产物 |
| --- | --- | --- | --- | --- |
| 2026-10-21 | 生成 hello world 页面 | 完成 | E3 | index.html |
```

- **只追加**，不改历史行；写错了就再追加一行说明，不改旧行。
- 完成 `plan` 条目时：删待办 + 追加一行，两件事一起做。
- 用命令追加，日期和列对齐都不会错：

```sh
node memory-kit/bin/memory.mjs done --unit <id> --task "完成了什么" --evidence E3 --artifact 产物
```

`done` 的输入规则（都是血眼泪换来的）：

| 输入 | 规则 |
| --- | --- |
| 任务 / 结果 / 产物 | 竖线、换行、制表符会被压成空格；单元格里不能有 `\|` |
| `--date` | 必须是合法的 `YYYY-MM-DD`；只影响任务行，不动头部 `updated` |
| `--evidence` | 必须是 `E0`–`E4`；省略时按 `E0` 记，并提示补证据 |
| 写入后校验 | 如果新内容不合法，**回滚文件**并报错，绝不留下坏表格 |

### 12.2 进度可视化（可选模块）

`memory-viz` 是独立模块，`install.sh --with-viz` 才会装。它只读不写，生成一个自包含 HTML：

```sh
node memory-viz/bin/viz.mjs --config memory/memory.config.json
```

输出 `memory/progress.html`，包含：单元卡片与完成比例、任务时间线、证据分布、未完成项（区分待办与待核对）。默认用 public 模式遮蔽变量，加 `--local` 才显示本机真值。

模块退出码非 0 即表示读取失败；它不做校验，校验永远由 `memory-kit check` 负责。

## 13. 与 git 集成

git 知道"改了什么、何时改的"，记忆只需要回答"这算不算一件完成的事"。两者衔接点只有两处：

### 13.1 记录时绑定提交

```sh
node memory-kit/bin/memory.mjs done --unit <id> --task "修好相机探测" --evidence E3 --commit
```

`--commit` 不带参数取 `HEAD`，带参数取指定 ref。记录时会把短哈希写进"产物"列（如 `probe.py · 提交 0a1b2c3`）。取不到 git 时只警告，不阻断记录。

### 13.2 检查漏记

```sh
node memory-kit/bin/memory.mjs git --unit <id> --limit 20
```

列出最近 20 条提交中、短哈希没有出现在任何单元正文里的那些，并给出可直接执行的 `done` 示例。

**它不是自动补记工具**：多数提交（同步、格式化、文档微调）不值得进台账。它只是把"可能漏了"的东西摆出来，由人决定。

### 13.3 反过来的纪律

记忆的改动必须提交到 git。理由不是"版本管理好看"，而是：契约升级要靠 git 回退，`migrate` 会拒绝在脏工作区执行；任务台账里引用的提交哈希也只有在历史里才成立。

`BootMemory.md` §7.4 把它列为硬规则之一。
